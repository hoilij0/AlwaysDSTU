# Always DSTU — общий контекст проекта

Этот файл — единая рабочая памятка команды: здесь собраны принятые в переписке решения, состояние репозитория и следующий план по ЛР6–7. Он помогает продолжить работу без восстановления истории чата. Это не замена заданию преподавателя и утверждённым отчётам.

## Как поддерживать общий контекст

- Перед началом работы каждый участник обновляет локальную копию из ветки `main` и сверяется с этим файлом.
- Изменения требований сначала обсуждаются всеми участниками. После общего решения обновляются этот файл и, если нужно, соответствующий отчёт или ТЗ.
- Для каждого общего файла назначается один редактор на время правок. Остальные проверяют его версию и присылают замечания; параллельные копии Word-файла не создаются.
- Изменения публикуются в GitHub небольшими коммитами. Перед объединением участник команды проверяет, что обновление не противоречит ЛР1 и заданию преподавателя.
- Имена ответственных за ЛР6, ЛР7 и итоговую проверку пока не распределены. Не считать решение одного участника согласованным всей командой, пока оно не подтверждено остальными.

Если новое указание преподавателя расходится с этим файлом, приоритет у преподавателя. Команда фиксирует новое решение здесь, чтобы все работали по одной версии.

## Проект в двух словах

Always DSTU — учебный проект для просмотра расписания ДГТУ без постоянного доступа к интернету. Основная идея: сохранить расписание выбранной группы, показывать его офлайн, добавлять простые заметки к парам и после обновления расписания помогать увидеть, что изменилось.

Над проектом работают Дылевский, Мещеряков, Яблоновский и Таран; учебная группа — ВИС32, ДГТУ.

## Зафиксированные решения и границы

- Сейчас сначала разрабатывается настольный прототип на ноутбуке. К мобильной версии вернёмся позже, после согласования с преподавателем. Ранний замысел ЛР1 описывает Android, а отчёт ЛР5 уже фиксирует настольный этап — в новых материалах важно не смешивать эти два этапа.
- Пользователь выбрал оформление по макетам ЛР2: тёмно-синюю шапку, синие акценты, карточки занятий и цветные отметки изменений. В профиле доступны светлая и тёмная тема. Настольный экран адаптирован к широкому окну; мобильное приложение ещё не реализовано, интерфейс Tkinter не переносится на Android автоматически.
- Пользователь попросил упростить интерфейс по направлению к IKMS: карточки открываются целиком без отдельной кнопки, а вместо месячного календаря и таблицы оставлены один экран дня и компактная полоска недели. Выбор группы находится только в профиле; обновление находится рядом с заголовком расписания. Клавиатурное открытие карточек сохранено. Прямая визуальная сверка со скриншотами IKMS пока не проведена.
- Пользователь предложил заменить часть кнопок иконками и улучшить визуальный стиль с помощью библиотеки. Набор иконок и выбор библиотеки ещё нужно согласовать с ним; до согласования их не менять. Ранее существовавшая таблица со значком заметки по последнему решению пользователя убрана; полная заметка открывается нажатием карточки пары.
- Настольный прототип остаётся на Python 3.12 и Tkinter. В ходе ЛР6 добавлены карточки расписания, получение данных из API ДГТУ, локальное сохранение снимков в PostgreSQL, CRUD заметок, аналитика по периоду и сравнение версий. Хранится выбранный месяц и дополнительные дни соседних месяцев для полных граничных недель; два последних снимка месяца остаются для сравнения. При успешной загрузке другого месяца прежний кэш очищается транзакционно, а при сетевой ошибке сохраняется. Отчёт подготовлен; остаются командная проверка и снимок доски для отчёта.
- Для будущей работы с данными использовать `PostgreSQL`, не SQLite. В старом тексте ЛР1 название написано с опечаткой; пользователь отдельно уточнил правильное написание. Существующую ЛР1 без отдельной просьбы не переписывать.
- Выбор группы должен быть изменяемым: пользователь может открыть расписание и заметки другой группы. Регистрация и пароль не входят в текущий замысел; пользователь выбрал локальный ник без регистрации для подписи заметок.
- Заметки задуманы как простые текстовые заметки к отдельным занятиям. В переписке обсуждалось, что их смогут видеть другие смотрящие расписание группы, но ЛР1 исключает синхронизацию заметок между устройствами. До реализации общего доступа команда должна согласовать с преподавателем, что именно означает «видны всем» для настольного этапа.
- Для получения расписания в текущем прототипе выбран способ из IKMS: JSON-запросы к `https://edu.donstu.ru/api/` (`raspGrouplist` и `Rasp?idGroup=...`). Пользователь подтвердил, что из IKMS берём именно метод получения расписания, а не его стек и архитектуру. Живой запрос для ВИС32 проверен 23.11.2026; API вернуло 269 занятий за сентябрь–декабрь 2026 года. Это пока подтверждение текущего прототипа, а не отдельное решение всей команды.
- В проектной идее есть офлайн-просмотр, отметка времени последней синхронизации и показ различий между предыдущей и новой версиями расписания. В ЛР1 не предусмотрены фоновая синхронизация и push-уведомления; не обещать их в текущем прототипе.
- При переходе к другому месяцу старый месячный кэш удаляется после успешной загрузки нового; дополнительно по решению пользователя сохраняются граничные дни соседних месяцев для недельной статистики офлайн.
- Файл `Always DSTU.sql` расширяет схему ЛР4 таблицами `detached_notes`, `app_settings`, `boundary_lessons` и `boundary_cache_state`. Остальные таблицы — `groups`, `schedule_snapshots`, `lessons`, `notes`, `sync_log`; для подписи добавлено поле автора заметки.

- В корне лежат отчёты ЛР1–ЛР6, Канбан-доска, SQL-файл, README, настольный прототип и визуальные материалы. Папка с материалами преподавателя намеренно не включена в репозиторий.

- В текущем файле ЛР5 остаются места для скриншотов приложения и Канбан-доски. Перед итоговой сдачей нужно проверить, что в копии, которую увидит преподаватель, на этих местах действительно вставлены скриншоты.

## ЛР6 — реализация базового функционала

По заданию цель ЛР6 — реализовать первый рабочий сценарий на основе модели данных из ЛР4 и макетов из ЛР2: пользователь вводит данные через форму, сохраняет их, а затем видит запись в списке. В отчёте нужно показать актуальное состояние Канбан-доски.

В отчёт ЛР6 включить:

1. Краткое описание реализованных функций с привязкой к кодам ФЗ из ТЗ.
2. Скриншот заполненной формы ввода и скриншот главного окна, где новая запись видна в списке.
3. Ключевой фрагмент логики сохранения — ориентир задания: 10–20 строк кода с обработчиком кнопки и записью в PostgreSQL либо эквивалентный скриншот настройки, если команда выберет другой разрешённый инструмент.
4. Скриншот обновлённой Канбан-доски.

После последнего изменения интерфейса табличный список убран по просьбе пользователя: карточка пары показывает отметку о заметке, а полный текст открывается нажатием карточки. В отчёт добавлены соответствующие снимки; нужно сверить с преподавателем, достаточно ли их для требования показать введённую запись в списке.

### Порядок работы над ЛР6

1. До кодирования команда сверяет ТЗ, SQL и текущий каркас; назначает одного редактора отчёта и владельцев отдельных задач. Не создавать параллельные версии программы или отчёта.
2. Сначала довести до конца один сквозной сценарий: открыть приложение, показать занятие, добавить связанную с ним заметку, сохранить данные в PostgreSQL и увидеть результат в интерфейсе. Этот первый срез теперь реализован и проверен на данных ВИС32.
3. Затем реализовывать и проверять остальные функции ФЗ-01–ФЗ-05 в согласованном объёме. В ТЗ заявлены ввод, хранение, отображение, редактирование/удаление заметки и аналитика по занятиям/изменениям расписания; не отмечать функцию выполненной, пока её можно продемонстрировать.
4. Интеграция чтения расписания с API ДГТУ реализована как первый вариант; сетевую доступность в тестовой среде уже проверили. Межустройственная синхронизация заметок не реализована и не должна считаться готовой только на основании макетов.
5. После каждой завершённой задачи обновлять её статус на общей Канбан-доске и сохранять доказательство результата.
6. Перед завершением ЛР6 участник-проверяющий запускает приложение с чистого старта и проверяет, что данные сохраняются и показываются без ошибки.

## ЛР7 — тестирование и итоговый отчёт

По заданию ЛР7 нужно вручную выполнить три простых теста, показать результат системы на скриншотах, перенести все карточки Канбан-доски в «Готово» и объединить отчёты ЛР1–ЛР6 в одну пояснительную записку с титульным листом.

Для каждой проверки записать код ФЗ, действие и входные данные, ожидаемый результат, фактический результат и статус «Пройден» или «Сбой». Набор из трёх тестов согласовать с реализованными функциями; в совокупности он должен проверять успешный ввод/сохранение/отображение, обработку некорректного ввода и одну из функций изменения или аналитики. Если ТЗ или преподаватель потребует полного покрытия ФЗ-01–ФЗ-05, три сценария могут проверять несколько функций каждый.

Перед сдачей ЛР7:

- повторно запустить приложение и пройти тесты на демонстрационном наборе данных;
- вставить скриншоты тестирования и финального состояния Канбан-доски;
- собрать согласованные версии ЛР1–ЛР6 в один файл и проверить, что описания совпадают с фактической реализацией;
- проверить титульный лист, состав команды, написание `PostgreSQL` и отсутствие незаполненных заглушек.

## Фактический прогресс ЛР6 на 24.11.2026

- Главный экран Tkinter показывает полоску недели и карточки выбранного дня; месячный календарь и табличный список удалены из интерфейса по просьбе пользователя. Выбор и поиск группы находятся в профиле, там же можно выбрать светлую или тёмную тему. Доступны загрузка справочника, ручное обновление и фоновая проверка API при запуске. После перезапуска без интернета поиск доступен по группам, сохранённым локально; полный справочник отдельно не кэшируется.
- Данные читаются из локальной PostgreSQL; приложение сохраняет снимки расписания и журнал успешных/неудачных синхронизаций. Пустой ответ, ответ с ошибкой или некорректными строками не заменяет кэш. Повторная загрузка неизменившихся занятий не создаёт дубликат снимка.
- Негативный статус ответа API и некорректные строки отклоняются. Дополнительно для того же месяца действует эвристика: если ранее было от шести занятий, а получено менее половины, кэш остаётся до явного подтверждения при ручной синхронизации. Счётчик не доказывает полноту ответа и может сработать при реальных массовых изменениях.
- Форма заметки поддерживает создание, редактирование и удаление с подтверждением. Ник задаётся один раз при настройке локального профиля или позднее в настройках, а не в каждой заметке. Изменение профиля не переписывает прежние подписи, но при последующем редактировании заметка подписывается текущим ником. Старые неподписанные заметки сохраняются. Очистка кэша доступна в настройках и удаляет снимки, занятия и связанные заметки, но сохраняет группу и журнал. Межустройственной синхронизации заметок нет.
- При переключении месяца и при изменениях расписания заметки сохраняются отдельно, если нужная пара отсутствует; их можно просматривать, редактировать и удалять через «Другие сохранённые заметки». При повторной загрузке подходящей пары связь восстанавливается, если сопоставление однозначно. Явная очистка кэша группы удаляет и эти заметки после подтверждения.
- Операции с заметками сериализуются с обновлением и очисткой той же группы. Если другое окно уже сменило снимок, сохранение в устаревшее занятие отклоняется с предложением скопировать черновик. Это защита локальной БД, а не межустройственная синхронизация.
- Добавлена ФЗ-05: приложение считает число занятий и суммарную длительность за день, неделю или месяц, а также сопоставляет два последних снимка и показывает добавленные, отменённые и изменённые занятия. Если две разные дисциплины поменялись временем, в первую очередь сопоставляются сами дисциплины. Неоднозначные повторяющиеся пары не помечаются как изменение без надёжного совпадения. Сопоставление основано на признаках занятия, поскольку в модели нет постоянного идентификатора источника; сложные замены могут быть показаны как добавление и отмена.
- После успешной синхронизации в строке состояния показывается отсутствие изменений либо число добавленных, отменённых и изменённых пар. Это внутренняя индикация открытого приложения, а не системное push-уведомление.
- Если неделя пересекает границу месяцев, офлайн-расчёт включает сохранённые соседние дни; для кэша старой версии требуется однократная синхронизация. Полнота зависит от данных сайта, при недостаточном диапазоне ответа показывается предупреждение. По кнопке можно временно рассчитать неделю по API без изменения кэша. Ранее запрос для ВИС32 за 30.11–06.12.2026 вернул 14 занятий и 1330 минут.
- Локальная БД содержит один текущий снимок ВИС32 на 79 занятий за ноябрь 2026 года (02.11–30.11); он получен фильтрацией ранее загруженного ответа API. Заметок в тестовой БД сейчас нет.
- Автоматические тесты проверяют разбор API, фильтрацию месяца, аналитику и историю снимков. Интеграционные тесты с реальной PostgreSQL проверяют сохранность заметок, неоднозначные повторяющиеся пары, явную очистку, отсутствие лишнего снимка и откат операции при ошибке. Ранее полный Tkinter + PostgreSQL smoke-тест прошёл с календарём, аналитикой и созданием/редактированием/удалением заметки.
- Под датами в недельной полоске показано число пар из кэша: 1 — зелёным, 2 — желтовато-зелёным, 3 — жёлтым, 4 и более — красным. Ноль означает отсутствие пар в сохранённых данных, прочерк — отсутствие данных о дне. Используются также сохранённые граничные дни соседнего месяца в пределах ответа сайта; полнота зависит от источника.
- Для HTTPS в Windows используется `truststore`: после исправления проверки сертификата живой запрос 23.11.2026 вернул 3094 группы и 79 пар ВИС32 за ноябрь. Прошёл 81 тест, включая PostgreSQL, окно с тестовыми данными, запускатель EXE и сквозной тест окна с PostgreSQL и имитацией ошибки сети. Проверены цветные счётчики в обеих темах и граничные дни, выбор темы и группы в профиле, карточки и управление клавиатурой, сохранение черновика при смене темы и кэша при переходе месяца офлайн, просмотр заметки, фильтр изменений и недельная аналитика.
- На этом ноутбуке отдельно проверена настройка с новым виртуальным окружением: установка из `requirements.txt`, активация в PowerShell, повторное применение схемы, запуск окна с локальной PostgreSQL и HTTPS-запрос к API. Временное окружение после проверки удалено; основной `.venv` сохранён. Проверка выполнялась на том же компьютере и не заменяет установку участниками команды.
- До завершения ЛР6 остаются проверка API-синхронизации на компьютерах участников, командный запуск с чистой настройкой и снимок Канбан-доски для отчёта.

### Сверка функций с ТЗ ЛР1

| Функция | Что работает в текущем настольном прототипе | Что ещё важно согласовать или проверить |
| --- | --- | --- |
| ФЗ-01 — ввод | Выбор группы; ввод и проверка непустой заметки и локального ника. Проверено в сценариях окна. | Ник не подтверждает личность и не создаёт учётную запись. |
| ФЗ-02 — хранение | PostgreSQL хранит группу, два последних снимка одного месяца и локальные заметки. Совпадающие записи пары и заметки к ней ограничены индексами; неподходящие к новому снимку заметки сохраняются отдельно. Проверено интеграционными тестами БД. | Между устройствами заметки не синхронизируются. Их общий доступ противоречит текущей границе ЛР1 и требует уточнения у команды и преподавателя. |
| ФЗ-03 — отображение | Расписание показано карточками выбранного дня с датой, временем, дисциплиной, преподавателем, аудиторией и отметкой заметки. Нажатие на пару открывает полный текст. Сохранённый месяц открывается без сайта. | Проверить удобство интерфейса на ноутбуках участников и собрать реальные скриншоты для отчёта. |
| ФЗ-04 — изменение | Заметку к паре или сохранённую отдельно можно изменить и удалить с подтверждением; очистка кэша группы удаляет снимки и её заметки после подтверждения. | Проверить сценарий вручную перед демонстрацией; журнал синхронизаций при очистке сохраняется. |
| ФЗ-05 — аналитика | Считаются число пар и минуты за день, неделю и месяц; последние два снимка сравниваются на добавления, отмены и изменения. Для граничных недель используются сохранённые соседние дни. | Полнота зависит от ответа API; старый кэш нужно пересинхронизировать для сохранения соседних дней. Пустой ответ API сохраняет прежний кэш и не считается подтверждением отмены всех занятий. |

Большинство автотестов окна используют тестовый API и хранилище; интеграционные тесты используют PostgreSQL. Сквозной тест дополнительно проверяет сохранение заметки через окно, повторный запуск с реальной PostgreSQL и поведение при имитации сетевой ошибки. Живой запрос API и запуск настольного окна с локальной БД проверены на текущем ноутбуке, но это не заменяет командную проверку на другом устройстве. Последовательность ручной проверки записана в `AlwaysDSTU/README.md`. Подготовлен отчёт ЛР6 со снимками приложения на демонстрационных данных и таблицей состояния доски `KANBAN.html`; для буквального выполнения требования задания ещё нужен снимок самой доски. Также с преподавателем нужно согласовать, достаточно ли отметки о заметке на карточке вместо полного текста в табличном списке.
